# 平台适配

这是提示词编写策略，不是平台能力清单。只阅读并应用目标平台对应项。保留同一目标与验收标准，只调整承载方式；平台或版本不明确时先交付通用文本，不强迫用户选模型。具体 API 字段、参数、变量语法、工具和限制须以实际环境或官方文档核实。

## ChatGPT

普通聊天交付可直接粘贴的完整提示词。若用户明确要可配置的系统指令，分离稳定行为规则与单次任务输入；不能把聊天框文本冒充真正的系统消息。只有环境提供搜索、附件或工具时才写依赖它们的执行指令，否则定义缺失时的回退。需要可核查结果时要求证据与简短理由，不要求展示内部思维链。

## Claude

长资料或多种输入可用语义明确、成对闭合的标签，如 `<source_material>`、`<examples>`、`<output_requirements>`，分开素材与指令。不要无意义地把每句话包装成标签。系统规则和单次用户输入仅在支持相应配置的场景分开交付。

## Gemini

任务、限制与验收要求直接表达，删除反复角色设定和同义强调。多模态输入明确指向对应图片、页面或片段，并说明需观察的对象、关系和输出内容；没有附件访问能力时不要假设模型已读到文件。避免套用未经核实的版本专属参数。

## Dify

区分工作流结构、LLM 节点提示词和输入变量。稳定规则放在可用的指令配置中，动态内容从实际节点变量注入；优先保留用户已有变量与字段名。通用 `{{变量名}}` 仅作设计占位符，未核实前不声称可直接作为 Dify 节点引用执行。需要结构化输出时明确字段、类型、必填项、空值和失败处理；只有目标节点确实支持时才提供对应结构化配置。涉及检索时把召回内容作为资料，定义无命中和证据冲突时的回退。不要把一段提示词描述成已部署的工作流。

## 图像模型

内部用五块结构澄清需求，最终通常合并成视觉描述：主体 → 动作／关系 → 场景 → 构图／视角 → 光线／色彩 → 风格／材质 → 必须保留或排除项。画面文字逐字引用；编辑任务明确要改什么和要保留什么，并指明参考图用途。把“高级感”等抽象词转成留白、配色、材质或光线等视觉特征。宽高比、尺寸、负面提示词和权重语法只有确认支持后才使用；不要默认输出文本模型的五个标题或强制英文。

## 视频模型

描述主体、场景、动作时间顺序、镜头运动、节奏、光线及连续性要求。区分主体运动和相机运动，避免一个短镜头塞入多个矛盾动作。多镜头时用简短镜头表，定义衔接与人物／物体的一致性；时长和时间点按用户要求或已知限制设定。参考素材、首尾帧、音频和对白只在能力确认后写为可执行输入，否则注明为创作意图。编辑时保留用户要求的角色、画面和节奏，不擅自重新设计整个作品。
